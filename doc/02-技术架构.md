## 2. 技术选型

| 层 | 选型 | 原因 |
| --- | --- | --- |
| 前端框架 | React 19 + TypeScript | 组件化、类型约束、生态成熟 |
| 构建 | Vite 6 | 启动快、配置简单、构建产物小 |
| 状态 | Zustand + Immer | 编辑器状态集中、更新直观、样板代码少 |
| 表单/校验 | Zod | 登录/注册前端校验，类型友好 |
| 路由 | React Router 7 + HashRouter | 静态托管无需服务端路由回退 |
| 后端 | Spring Boot 4.1.2 + Java 21 | 成熟的 Web/安全/JPA/事务体系 |
| 安全 | Spring Security Session + CSRF | 同源 Web 应用的简单可靠方案 |
| 持久化 | JPA + Hibernate | 实体和事务管理 |
| 迁移 | Flyway | 版本化建表，H2/PostgreSQL 共用 |
| 开发库 | H2 文件模式 | 无需额外服务，便于本地启动 |
| 生产库 | PostgreSQL 16 | 稳定、通用、易于容器化 |
| AI | DeepSeek Chat Completions | JSON 输出、中文能力、兼容接口 |
| 导出 | react-dom/server + JSZip | 复用渲染器，浏览器端打包 |
| 图片 | 本地文件系统 + 数据库元数据 | MVP 简单；生产可替换对象存储 |

## 4. 核心数据流

### 4.1 加载项目

```text
EditorPage useEffect
  → GET /api/projects/{id}
  → ProjectService.get
  → 读取 project.spec_json + chat_message + latestRevision
  → EditorStore.loadProject
  → PageRenderer 渲染
```

### 4.2 手工编辑

```text
PageRenderer 点击/输入
  → EditorStore.updateText / updateImage / updateTheme / ...
  → Immer 更新 spec
  → history 记录（交互开始时快照）
  → changeCounter + 1
  → 900ms 防抖
  → PUT /api/projects/{id}/draft { spec, version }
  → 后端校验 + 检查 expectedVersion
  → project.@Version 自增
  → 返回新版本号
  → 前端 savedCounter / saveStatus 更新
```

### 4.3 AI 对话

```text
ChatPanel.submit
  → EditorStore.sendMessage
  → 确保草稿已保存
  → POST /api/projects/{id}/messages
  → ChatService：
      空页面 或 含“重新生成/换一版/重做” → generate
      其他 → edit
  → Mock 或 DeepSeek
  → 编辑模式：SpecPatchApplier.apply
  → PageSpecValidator.validate
  → 更新 project.spec_json，project.version 自增
  → 写 project_revision（AI 快照）
  → 写 assistant chat_message
  → 返回 userMessage + assistantMessage + spec + version
  → 前端替换 spec，清除 selection，刷新画布
```

### 4.4 导出

```text
EditorPage.handleExport
  → 如未保存先 save
  → exportStaticSite(spec, projectName)
  → collectImages(spec)
  → fetch 每张图片（带 Cookie）
  → 去重后写入 assets/image-N.ext
  → cloneSpec 并替换图片路径
  → renderToStaticMarkup(<PageRenderer spec={exported} />)
  → 内联 page.css
  → JSZip 打包 index.html + assets/
  → 浏览器下载
```

## 5. 关键架构决策

### 5.1 用 PageSpec 而不是 AI 直接生成 HTML

**决策**：AI 输出固定结构的 JSON，前端通过组件库渲染。

**原因**：

- 结构可控，避免不可维护的 HTML。
- 服务端可以校验组件白名单和字段范围。
- 编辑器和导出共享同一份渲染逻辑。
- 局部修改可以精确到 JSON 路径。

**代价**：

- 组件库和字段协议需要维护。
- AI 不能自由创造全新视觉结构。
- 新组件需要前端、后端、提示词同时更新。

### 5.2 手工编辑与 AI 修改共享同一份 PageSpec

**决策**：用户操作和 AI 修改都落到同一份规格。

**原因**：避免出现「AI 版本」和「用户版本」两套真相。

**现状**：用户手工修改会在 `fieldMeta` 标记 `source: user`，但 AI 目前不会读取 `fieldMeta`，主要依赖提示词要求保留用户内容。后续应把 `fieldMeta` 纳入 AI 上下文或做字段级保护。

### 5.3 AI 编辑优先使用 JSON Patch

**决策**：页面非空时，默认让 AI 返回局部 Patch，而不是完整页面。

**原因**：

- 减少模型输出体积和随机性。
- 降低误改其他区块的概率。
- 便于限制可修改路径。

**限制**：Patch 仅允许 `/theme`、`/meta`、`/sections`，禁止 `/fieldMeta`；支持 `replace`、`add`、`remove`；应用后仍会做完整 PageSpec 校验。

### 5.4 开发 H2、生产 PostgreSQL

**决策**：同一套 JPA 实体和 Flyway SQL 适配两种数据库。

**原因**：本地零依赖启动，生产使用成熟数据库。

**注意**：H2 使用 PostgreSQL 兼容模式；迁移 SQL 尽量保持标准 SQL。当前只有 V1 迁移。

### 5.5 Session + CSRF 而不是 JWT

**决策**：同源 Web 应用使用 HttpSession 和 Cookie CSRF。

**原因**：

- 浏览器端不需要管理 Token 存储。
- 退出登录可以服务端销毁会话。
- Spring Security 原生支持。

**代价**：默认会话在应用内存，重启会掉登录；多实例需要 Spring Session JDBC/Redis。

### 5.6 客户端导出

**决策**：导出在浏览器完成，使用 `react-dom/server` 和 JSZip。

**原因**：

- 复用现有 React 渲染器，避免服务端再造一套模板。
- 不引入 Puppeteer/无头浏览器依赖。
- 用户可以立即下载。

**代价**：导出依赖浏览器环境；图片需要逐个 fetch；大页面可能占用较多内存；没有服务端审计和异步任务能力。

### 5.7 Mock 优先、DeepSeek 可选

**决策**：默认 Mock，有 Key 时切换 DeepSeek，失败自动降级 Mock。

**原因**：保证项目开箱可运行，不被外部 API 阻塞。

**代价**：Mock 只能覆盖有限指令；真实模型的提示词和稳定性仍需单独调优。

## 7. 架构风险

1. **会话在内存**：应用重启或多实例会丢失登录态。
2. **AI 与手工保存并发**：聊天接口不带 expectedVersion，多标签页同时操作可能覆盖。
3. **fieldMeta 未闭环**：目前只记录，不参与 AI 保护。
4. **图片本地存储**：容器迁移、扩容和备份需要额外处理。
5. **导出在客户端**：大页面、图片多时可能慢或占用内存。
6. **缺少服务端限流**：AI 和上传接口没有速率限制。
7. **没有端到端测试**：关键编辑器交互仍依赖手工回归。
